# 项目方案与进度

## 背景

本项目整理自 2026-10-23 的“修复 Codex 项目排序”聊天。
该次调查中，聊天的最近更新排序没有让侧边栏项目持续按活动时间上移；
曾经通过应用工具完成一次手动重排。

用户认可的方向是：对话结束事件触发检查，仅在项目顺序确实变化时执行重排。

## 已实现的处理流程

```text
agent-turn-complete 事件
  → 转发原有通知
  → 获取进程锁
  → 读取当前项目清单、分区顺序和本机对话活动时间
  → 计算默认项目区域的目标顺序
  → 顺序一致：退出
  → 顺序不同：重读分区，调用 App Tools 排序接口，回读验证
```

顺序一致时，后续对话只需要一次本地检查，不进行排序写入。
时间相同的项目保留已有相对顺序；没有活动记录的项目排在有活动记录的项目之后。

## 阶段

1. **已完成：仓库初始化。** 建立项目说明、开发规则和 Git 基线。
2. **已完成：整理排序规划器。** 迁入前期只读脚本，真实聊天数据和状态快照留在原目录。
3. **已完成：接通客户端写入。** 通过 App Tools 本地命名管道调用列表和排序工具，实际重排及回读验证通过。
4. **已完成：接入对话完成事件。** 使用用户级 `notify`，保留原有通知，支持并发串行处理与失败静默退出。
5. **已完成：安装与卸载。** 使用配置 API、版本检查和本地备份，重复安装不重复包裹。

## 实现选择

前期没有找到写入方式；本次从已安装的 App Tools 插件代码确认了本地管道协议，
并验证脚本可在保留聊天身份的情况下调用 `list_projects`、`list_threads` 和 `reorder_sidebar_projects`。
客户端状态文件和 SQLite 始终只读，更新通过客户端工具执行。

当前机器已有官方 `notify` 回调，因此采用 `agent-turn-complete` 接入。
代码也能解析 `Stop` 输入，但未安装额外的 Stop Hook，避免对同一轮重复执行。
没有定时任务、模型调用和常驻进程。

## 当前边界

只排序默认区域的本机 Codex 项目；置顶、自定义分区、远程和 ChatGPT 项目保持原安排。
本地活动时间优先使用 `recency_at_ms`，避免元数据更新把旧对话当作新活动。
没有可用活动时间时，项目保留相对次序并排在有活动记录的项目之后。

命名管道和客户端私有数据结构可能随版本变化；缺少接口或读到不支持的结构时记录错误并退出。
App Tools 没有条件写入接口，写入前重读分区可以缩小竞争窗口，但不是跨客户端事务。

官方事件说明：https://learn.chatgpt.com/docs/config-file/config-advanced#notifications
